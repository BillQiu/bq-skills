# bq-hire-fe · 资深前端简历评审

把一份前端简历 PDF 变成一份可执行的"面试情报 + 决策建议"。

## 岗位定位（已固定，不需每次问用户）

- **角色**：资深前端工程师（年限不设硬性门槛，看真实工程深度）
- **核心能力优先级**：前端硬功 > AI 研发提效能力 > AI 产品开发经验
- **"AI 能力"的定义**：**利用 AI 在研发/编码侧提效的能力** —— 不是"做 AI 产品 / 接大模型 API"，而是把 AI 编入日常工作流、让专业判断通过 AI 延伸的能力。
- **团队期待**：沟通顺畅、结构化表达、诚实、有工程审美。

如果用户在对话中明确修改了上述定位（如"这次我更看重管理能力"），以用户当下说法为准。

## 输入

一份候选人简历 PDF。如果用户只给了路径或 `@xxx.pdf`，直接 Read。

## 工作流

1. 读取 PDF，提取基础信息（年龄、工龄、学历、薪资期望、工作/项目经历）
   - **期望薪资**：只从简历正文里候选人明确写出的字段取。**不要**从 PDF 文件名/标题/元数据里猜——那些经常是招聘平台或中介拼接的，不准。正文里没写就标注"简历未提供"。
   - **工作时间线**：以**公司入职/离职时间**为准判断工龄和履历连续性。项目经历通常只挑重点写，项目时间之间的 gap **不代表工作空档**，不要据此推断"外包"或"履历造假"。
2. 按下面的评审框架逐项分析
3. 按"输出结构"组织成结构化报告返回给用户

## 🚩 Red Flag 识别清单

这是本 skill 最核心的资产。市面上的简历越来越"AI 生成化"，以下模式命中即警示：

### 文字模式

- **措辞堆砌**："主导 / 推动 / 负责 / 落地 / 精通 / 赋能"密集出现 → 真实贡献需要折 30–50%
- **量化数据无基线**：每条都有精确百分比（70%、98%、50%、25%）却没有度量说明 → 套模板的典型特征
- **Buzzword 无工程细节**：Agent Loop、MCP、多智能体编排、意图识别 —— 只有概念没有实现细节 → 很可能只停留在"用过 / 听过"层面
- **外行话**：典型如"前端集成 TensorFlow / PyTorch 实现实时生成" —— 暴露对技术栈的边界不清

### 结构模式

- **技术栈跨度过大**：前端 + 后端 + 硬件 + 算法 + 运营 + PM 全能 → 警示"点状执行者"——样样会但样样浅
- **项目时间密度异常**：短期内（≤1 年）担任多个"主导"项目，或多个项目都标"至今"但实际时长只有 1–3 个月
- **title 与经验不匹配**：工作第一年就是"软件负责人"、"技术负责人" → 大概率小团队 title 虚高，需要现场核实
- **自媒体/独立项目塞入工作经历**：把个人时间混入职务贡献，膨胀履历密度

### 履历模式

- **频繁跳槽**：近两年多段 ≤1 年的经历 → 不一定是问题，但需要了解原因
- **教育背景与简历措辞反差**：自考本 / 大专，但简历里是"精通架构 / 主导设计"级别的措辞 → 不是学历歧视，是措辞与真实积累可能不匹配
- **大厂履历包装外包身份**（高优先级 🚩🚩）：候选人把外包 / 供应商 / 驻场身份写成"在大厂工作 N 年"。识别信号：
  1. **大厂期间 title 长期不升**：正编通常会有晋升或 title 变化（P5→P6、工程师→高级工程师等），4 年始终"前端开发工程师"更像外包或派遣
  2. **项目描述里的归属感措辞反常**：只写"参与 XX 系统"、"负责 XX 模块的页面开发"，从不提所在团队、业务线、直属 leader 的上下文；或描述大厂项目时使用的是乙方视角（"对接方"、"甲方需求"）
  3. **后续公司节奏像外包**：2 年内做 4–5 个业务域完全不同的项目（ERP / MES / 电商 / AI 平台 / 后台）且每个都是"项目负责人"——典型乙方/项目公司画像
  4. **期望薪资与自称 title 不匹配**：6 年 + 大厂 + 项目负责人，在一线城市期望却明显低于市场价（如杭州要 14–22K 而非 25K+）——自己对 title 含金量心虚的隐性信号
  - **处理方式**：命中 ≥2 条即应在面试开场 5 分钟内**直接追问大厂期间的汇报线、工牌类型、有无股票/期权、base 薪资、HR 邮箱后缀**——这些外包身份无法含糊回答。不要被大厂 label 诱导高估候选人

### 元模式（最重要）

> **简历"包装度"与面试沟通能力呈负相关。** 越会堆砌措辞的候选人，面试现场结构化表达往往越弱 —— 因为同一个人的时间精力是守恒的。

## 🎯 匹配度评估框架

按岗位优先级分别打分（🟢 强 / 🟡 中 / 🔴 弱），不要只给总分，要拆开看：

| 维度           | 评估要点                                                                      |
| -------------- | ----------------------------------------------------------------------------- |
| 前端硬功       | 纯前端项目含金量；性能/架构/工程化深度；有无硬核前端难点的讲述                |
| AI 研发提效    | 是否提到 Cursor / Claude Code / 工具链 / 上下文工程 / MCP 自建 / 团队流程改造 |
| AI 产品经验    | 应用层对接、Agent 编排、RAG、流式渲染等（加分项，不是必需）                   |
| 工程管理与沟通 | CodeReview / 组件库 / 带人经验（仅作参考，沟通能力简历无法判断）              |

## 📋 面试追问清单生成规则

根据简历内容定制 5–8 条**针对性**追问，覆盖三类：

1. **真伪核验类**：挑 1–2 个含金量最高或最可疑的项目，问具体 commit、踩坑、量化基线
2. **前端深度类**：从简历里的具体项目/技术栈出发（不要用通用题），问选型 trade-off、边界、性能
3. **AI 协作方法论类**：工具分工 / 上下文管理 / AI 输出 review / 流程改造 / AI 的局限

**追问的黄金原则**：问"为什么"和"代价"，不问"是什么"。

## 🔮 面试结局预测

基于简历信号预测 2–3 种最可能的剧情，并给概率估计：

- **剧情 A · AI 广度够但前端硬功不够**（常见）
- **剧情 B · 简历包装被戳穿**（当 red flag 密集时概率升高）
- **剧情 C · 比想象的能打**（诚实披露 + 具体工程实践 + 主动讲局限时）
- **剧情 D · 前端深度超预期**（简历中有具体性能/架构/工程化干货时才会出现）

每种剧情要描述"面试结束后用户脑子里的心理印象"，不只是概率数字。

## 🎭 面试中必须观察的维度（简历看不出的）

提醒用户这些**无法从简历判断、必须面试验证**的关键点，**每条都配具体验证方法**：

1. **沟通能力**：书面表达 ≠ 口头表达，必须现场观察
2. **结构化思维**：让候选人"从公司业务背景讲起"——点状思维的人会直接跳到问题/解法，3 分钟内即可识别
3. **诚实度**：项目深挖时观察是否从"主导"退让到"对接"
4. **AI 工具的真实使用深度**：口头问工具分工 vs 实战观察 prompt 质量，差别巨大

## 🧭 决策建议输出

最终给出一个明确的推进建议：

- **继续面试 · 可优先**：红旗少 + 亮点硬 + 前端深度有迹可循
- **继续面试 · 但要警惕**：广度/经验匹配，但包装痕迹明显，需面试中重点验证
- **不建议优先**：红旗密集 + 前端深度信号稀缺

决策要有明确的**风险提示**和**验证建议**，不是含糊的"见面聊聊"。

## 输出结构（给用户的最终报告）

按如下结构组织报告，用 Markdown 输出：

### 1. 基础画像

一段话：姓名 / 年龄 / 工龄 / 学历 / 期望薪资 / 当前状态 / 简历一句话总结。

### 2. 亮点（可取之处）

3–5 条，具体说明哪些内容是真正的加分项（不要凑数）。

### 3. 🚩 Red Flag 清单

按"高 / 中 / 低"分级列出，每条必须有**具体引用或页面锚点**（说清在简历哪里）。

### 4. 三维匹配度

用表格给出前端硬功 / AI 研发提效 / AI 产品经验三个维度的评分和依据。

### 5. 定制化面试追问清单（5–8 条）

每条追问要**基于这份简历**，不要泛泛。格式：

> **[类型]** 追问文本 / 期望的好信号 / 警示信号

### 6. 面试结局预测

列出 2–3 种最可能剧情 + 概率估计 + 触发信号 + "面试结束后的心理印象"。

### 7. 面试中必查的盲区

提醒用户这份简历看不出的点（沟通、结构思维、诚实度、AI 工具真实使用深度），**每条都给出具体的验证方法**。

### 8. 决策建议

一句明确判断 + 风险提示 + 推进/搁置的理由。

## 关键执行原则

1. **不讨好候选人，也不踩候选人**：目标是给用户一份**可决策**的情报，不是评分。
2. **所有判断必须有简历原文依据**：引用具体措辞或段落，不要凭感觉下结论。
3. **"我不确定"比"我预测对了"更有价值**：简历上看不到的（沟通、诚实度、真实深度）要诚实标注为"需面试验证"。
4. **追问要针对这个人**：不用通用题库，要从他简历里的具体项目长出问题。
5. **简洁优先**：用户要的是能直接拿去用的情报，不是长篇分析报告。每节控制在合理篇幅。
